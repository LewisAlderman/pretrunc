# pretrunc design

Cut text at its start, middle or end so it fits a width, on one line or across N lines. Framework-agnostic TypeScript core, a Solid 2 adapter, and pretext for multi-line only. Built inside sprint-poker as a workspace package, then moved to its own repo; `sprint-poker#N` names an issue there, `#N` one here.

## Prior art and what this does differently

- `pretext-truncate` scans the last line backwards one character at a time, calling `prepare` twice on a fresh substring per step: O(n) measurement passes per cut. React only. End only.
- `pretext-ellipsis` hides the text until measured, then clips the last line with CSS `overflow: hidden` instead of computing a cut. React only.
- pretext's `pages/demos/ellipsis.model.ts` is the reference for browser behaviour: a line clamp ends the way `-webkit-line-clamp` does (the line breaks where it would without the clamp, the ellipsis follows if both fit, otherwise the line is cut after the last grapheme that leaves it room), and its middle cut keeps a path's file name. It finds cuts by asking for lines one candidate at a time.

pretrunc replaces candidate-by-candidate measuring with arithmetic over widths it already holds, confirmed by at most one or two real measurements, and in the common case none.

## Result: one number

A cut is two UTF-16 offsets into the prepared text: kept text is `[0, head) + [tail, length)`. One shape covers every mode: an end cut has `tail === length`, a start cut has `head === 0`, a middle cut has both, and text that fits has `head === tail === length`.

The two offsets pack into one number, `head * 2**26 + tail`, exact in a double for text under 2^26 UTF-16 units. `cut()` therefore allocates nothing, and a reactive memo over it compares by value: a resize that doesn't move the cut re-renders nothing in Solid, and in React a `useSyncExternalStore` snapshot stays equal. Helpers unpack it:

```ts
head(c); // Math.floor(c / 2**26)
tail(c); // c % 2**26
truncated(c); // head(c) < tail(c)
toText(p, c, ellipsis); // allocates; call it where you render
```

## Core API (`pretrunc`)

```ts
const p = prepare(text, font, { protect: /[^/]+$/g, letterSpacing: 0.5 });
const c = cut(p, width, {
  at: "middle", // "end" (default) | "start" | "middle"
  ratio: 0.5, // middle: the head's share of the room
  tailGraphemes: 8, // middle: keep the last 8 graphemes instead of a ratio
  tailMatch: 0, // middle: the tail starts at protected match 0 (a file name, an extension)
  words: true, // back off to a word boundary within a quarter of what that side keeps; { within: 24 } for 24 px; false never
  trim: true, // drop spaces and `,;:` beside the ellipsis
  ellipsis: "…", // a string, or a width in px for an element you render
});
```

`prepare` collapses white space the way `white-space: normal` paints it, and offsets refer to `p.text`, the collapsed string. Protected spans are a RegExp matched against that string, since offsets into the caller's text would shift when white space collapses; one without the g flag is copied with it, since `matchAll` throws on it otherwise. `font` is a CSS font shorthand, measured with canvas, or a `Face`: `canvasFace(font)`, `tableFace` from a metrics table (sprint-poker#54), or `face(measure)` over node-canvas or a test double. A `Face` is opaque: its caches are typed only inside pretrunc, so they can change without breaking anyone. `letterSpacing` is CSS `letter-spacing` in px.

### Names

Names are judged by how a call reads where it's made. A number or a boolean says nothing there, so each carries its role: `clamp` takes its line count as `lines` in its options, as `<Clamp>` does, since `clamp(p, 3, 240)` type-checked as readily as `clamp(p, 240, 3)`; the middle split's options are `tailGraphemes` and `tailMatch`, which name what each counts and keep clear of `tail(c)`, an offset; `words: { within: 24 }` says px where `words: 24` read as a count of words; `createCut` takes `separateEllipsis` among its props instead of a second, positional boolean. The canvas face is `canvasFace`, beside `tableFace` and clear of the DOM's `FontFace`. A component that hands values down through context is a provider in JSX, so the one that gives a list its font is `FontProvider`. Option names are kept whole in the bundle, so each costs its letters: the renames took the core 11 bytes.

### Measuring without measuring

The expensive operations are `Intl.Segmenter` and `measureText`. The core avoids both where it can.

1. **No segmenter for simple text.** Below U+0300 every UTF-16 unit is one grapheme, CRLF aside, and collapsing white space removes CRLF. One regex test decides whether the text needs `Intl.Segmenter` at all; one lazily created segmenter serves the rest.
2. **Shared widths per font.** Each font's face caches every width it measures. Characters below U+0300 are cached by code: a typed array for single characters, a flat 128 × 128 table for ASCII pairs, a numeric-keyed map for other pairs, and per ellipsis the kerning on each side of it. So preparing and cutting simple text builds no strings once the face is warm; graphemes, words and ellipses are cached by string. Simple text also shares one array of offsets 0, 1, 2… instead of allocating its own. A grapheme adds its advance plus the kerning from its pair to the running total. A table of 5,000 names in one font measures each distinct character and pair once, a few hundred `measureText` calls in all, not one per row per resize.
3. **Trust per word.** `prepare` measures each word whole, cached in the face, and compares it with the sum of its pairs. Within 0.01 px for every word, the pair model holds for the text, since nothing shapes across a space, and every cut of it is arithmetic: pair widths, plus the kerning on each side of the ellipsis. Otherwise (ligatures, Arabic joining, Indic shaping) the text is measured whole and each candidate cut is measured for real. Measuring each whole text instead was the first version; it was most of a cold `prepare`'s time (63 of 71 ms for 5,000 names in WebKit), and words repeat across rows where texts don't.

Canvas measures small emoji wider than the DOM paints them on macOS, as pretext documents. Wider means a shorter cut, so the contract holds without pretext's emoji correction.

### The cut

`prepare` stores grapheme start offsets, each grapheme's own width and a prefix sum `W[i]` of the first `i` graphemes, kerning included. Each step of the sum is clamped at 0, so binary search stays valid even with negative kerning. A tail's width is exact: `W[n] - W[t + 1]` plus grapheme `t` alone, since nothing precedes it but the ellipsis.

- **End:** the largest `h` with `W[h] ≤ room`. A galloping binary search, O(log d) for a cut d graphemes from the last.
- **Start:** the smallest `t` whose tail fits.
- **Middle (ratio):** the head takes the largest `h` within `ratio × room` and the tail the smallest `t` within the rest of the room, each against its own share. Neither takes the slack the other's rounding left: when the head borrowed it, a step of the width that let the tail grow by a grapheme took a grapheme back from the head, so the ellipsis wandered a grapheme one way and back as a box was dragged.
- **Middle (tail graphemes or a protected match):** fix `t`, then cut the head into the rest. If the fixed tail alone doesn't fit, fall back to the ratio. A protected match that the ratio's tail would split takes room from the head while all of it fits the room, instead of dropping whole the moment it outgrows the tail's share. One that doesn't fit the room goes whole and leaves the head all the room it frees. So a path with a protected file name cuts like an end cut until the name fits beside the ellipsis, then switches once to the name and what's left of the head; the switch happens at one width, never back and forth. A fixed tail never backs off to a word.

Each side's fit counts the kerning beside the ellipsis, a step or two past the binary search. Measured text then settles one grapheme at a time on real measurements, for the shaping across graphemes: shrink until it fits, then grow each side while one more fits, which also finds a longer cut that a ligature paints narrower. Trusted text needs no settling.

Engines differ on kerning across a line-break opportunity. WebKit lays out the text between two break opportunities as a run of its own, so kerning after a hyphen, a dash, CJK or the ellipsis never reaches the page, while Chrome, Firefox and canvas keep it: in Inter at 15 px, canvas puts "…To" at 29.96 px and WebKit lays it out at 30.47. Across a possible break the model counts kerning only when it widens, so it is never narrower than any engine's layout, and in Chrome and Firefox at most a fraction of a pixel loose. The trust check still compares canvas with the exact sum, and measured text adds back the kerning WebKit drops. Chrome also rounds a laid-out width up to the next 1/64 px, which the cut's 1/64 px slack covers.

Letter spacing is counted after every UTF-16 unit, the last included: WebKit spaces glyphs, several to a grapheme in Indic and Thai, so per grapheme ran 4 px over there, and per unit is never less than any engine. WebKit also turns kerning off under letter spacing while Chrome keeps it, so with letter spacing only kerning that widens counts, anywhere. The width that decides whether text fits whole is the same conservative sum, which can only cut a hair early.

The cut's helpers are module-level functions over module state, not closures: a cut runs to its end without calling out except to a face's measure, so a resize frame over thousands of rows allocates nothing per cut. Text with graphemes above U+0300 caches the kerning beside each ellipsis per text; simple text shares its face's. Per-grapheme word and trim flags come from `prepare`.

`prepare` runs `protect` once over the text as it will paint, and keeps the matches as offset pairs in order. Each pair's start is clipped to the text, but an end past it stays, so the last line's cut in `pretrunc/lines` still sees a match run on past its range. Marking every UTF-16 unit, as at first, took an array as long as the text, and in Chromium that allocation cost more than the regex. For 5,000 paths `protect` added a median 2.3 ms with marks and 0.8 ms with pairs. The regex itself is 0.5 to 0.8 ms of that, about 0.1 µs a text and once per `prepare`, never per cut. A regex-free `protect` was considered: ranges from the caller would refer to the text as given, not as `prepare` collapses its white space, and a function returning ranges would need checking for order and overlap. Either would save at most that 0.1 µs, so `protect` stays a regex.

Then the boundary passes, in order: back off to a word boundary inside the text if one lies within the backoff limit, snap out of protected matches (always towards keeping less), trim spaces and `,;:` beside the ellipsis. Each pass only removes graphemes. Removing a grapheme can widen shaped text, as when an Arabic letter loses its joining form, so the cut shrinks again once more at the end.

The backoff limit is a quarter of what that side keeps, not of the room. A limit tied to the room grew while a side's cut point held still on one grapheme, crossed the distance to a break partway, and snapped the side back a word, then forward again at the next grapheme: the flicker seen while dragging a box. Tied to the side, the limit holds still with the cut point, and each grapheme the side gains moves it a grapheme further from the break while the limit grows by a quarter of one, so a side that stops backing off never starts again until it passes a new break.

Each search gallops from where the last one on the same prepared text ended: it doubles its step until it brackets the answer, then bisects the bracket. A resize moves a cut a grapheme or two, so most searches end in two or three comparisons instead of five or six. Widths only move one way along the text, so the answer is the one a plain bisection finds, and a property checks that a text cut at a run of widths gives what a freshly prepared copy gives at each. The end each search takes as given, the empty head or the empty tail, is never measured, as in plain bisection. Over a drag of 5,000 rows through 40 one-pixel steps, it took end cuts from 24 to 22 ms in Chromium, 55 to 52 in Firefox and 17 to 16 in WebKit, and middle cuts, which search twice, from 57 to 49, 98 to 92 and 36 to 33. It cost 99 bytes. One search for both sides, the tail asked as the last start still too wide, came out 10 bytes larger: brotli packs two near-copies better than one with branches.

A secant search over the room was tried and dropped: it stalled on misses smaller than a grapheme, and one number cannot correct both sides of a middle cut.

## Multi-line API (`pretrunc/lines`)

```ts
const p = prepareLines(text, font, { whiteSpace: "pre-wrap", wordBreak, letterSpacing, protect });
const c = clamp(p, width, { lines: 3, at: "end", words: true, ellipsis: "…", after: moreWidth });
roomAfter(p, width); // px after the last line once expanded, where a "less" link would go
```

pretext collapses white space the way the core does, or keeps it in `pre-wrap` (with CRLF as one break), so its segments join to the text every offset refers to, `p.text`, and the same `head`, `tail` and `toText` helpers apply. `after` keeps room in px free after the text's end, for a "more" link; text that fits shows whole with nothing after it, so `after` takes no room then.

- **End:** walk the first N−1 lines with `layoutNextLineRange`, which builds no strings, then run the core's end cut from line N's start, `after` px narrower. The core prepares only the region a cut can keep, from line N's start to the end of the line after or to a hard break, and the region stays cached for the next cut at the same place. The text always goes on past the region, so the ellipsis always gets its room, even where line N ends at a hard break. Kept text rendered in a wrapping block re-wraps to the same first N−1 lines, or fewer when the cut shortens line N's first word enough to fit on the line before.
- **Start and middle:** the head keeps the lines before the one at `ratio × N` and, on that line, an end cut of what's left of `ratio × N × width` (nothing, for a start cut). The tail's first line gets the rest of that line, whatever the head kept of its share. The tail's candidate starts are word starts after the head, or grapheme starts without word preference or when no word start fits. Both are tables of typed arrays kept on the prepared text: offset, segment, grapheme index and a trim flag per start. Word starts are pretext's segment starts, so their table needs no segmenter; the grapheme table segments the text once, the first time a clamp needs it. A clamp binary-searches the first start after the head and lists the candidates in one shared, growable `Int32Array`. Segmenting on every clamp, as at first, was 80% of a warm start or middle clamp; the tables made 500 paragraphs clamp 5 times faster warm in Chromium and WebKit and 1.4 times in Firefox, and 2.5 times faster cold in Chromium and WebKit. pretext's line streams accept any cursor, including one partway through a word, and a width per line, so each candidate is a probe of the lines left, the first beside the head and the ellipsis, laid out from that cursor over the prepared handle: no new `prepare`, pure arithmetic. A binary search finds the first candidate that fits. If even no tail runs over, as when `after` leaves less room than the head took, the head gives up a grapheme and the search runs again.

The model lays head and tail out apart, and the joined line can wrap differently: a tail that begins mid-word can't break where a line start could, and an ellipsis can end the line before. So start and middle cuts settle on a real layout of the joined text: later while it runs over, and for a start cut, earlier while the start before still fits. A middle cut doesn't move earlier, which would take the head's slack. Every layout, the model's and the check's, is at the box's own width; the check used to run 1/64 px narrower, and a line that fit the model but not the check shifted the tail at some widths and not the next. That layout is the stricter of pretext's plain and rich-inline layouts, which disagree in some mixes, with a text ellipsis in one run with the text, as it renders, and a width-only ellipsis and `after` as boxes. A tail never starts at the head's end, since a cut that removes nothing isn't a cut.

In a middle clamp the head's last word and the tail can wrap together: one more letter of head can push the ellipsis or the tail's first word to the next line and cost the tail more than the head gained, so a wider box showed less (sprint-poker#90). When the real layout refuses the model's tail start, which is when they wrap together, the clamp also tries every shorter head back to the start of its line or of its last word, whichever is earlier, and keeps the one that shows the most text, white space aside, the longest on a tie. Each try is a tail search with real layouts, but only clamps where the layout slipped pay for it; the benchmark's middle clamps didn't move. A rarer shape remains, where the ellipsis or the tail's first word wraps and the better cut lies outside those heads, losing part of one word in about one case in 100,000 (#1). Taking the best of every head would end it but trade it for flicker, since on ordinary text many heads tie within a letter; a break opportunity after the ellipsis would end it too, but every caller building strings from `pretrunc/lines` would have to add one or risk overflow.

In `pre-wrap` the core counts a tab as the widest it can advance, and the layout check also tries each tab as that many no-break spaces held to the text around it: Chrome and WebKit let a tab hang at a line's end and Firefox keeps it with the word before. The widest isn't eight spaces. CSS Text says a tab less than half a `ch` from its next stop goes to the stop after; Firefox and WebKit do that and Chrome doesn't, so in Inter at 15 px `中文⇥` puts the text after the tab at 67.5 px in WebKit and 33.75 in Chrome. So a tab counts eight spaces and half a "0" (sprint-poker#76). pretext's model knows neither, so tabbed text shows whole only when it also fits with its tabs at their widest, a clamp works within the lines the model has when the model fits the text in fewer, and an end clamp of tabbed text gives up graphemes until the real layout check passes, as start and middle clamps already did.

## No canvas (`pretrunc/metrics`)

```ts
// vp run metrics node_modules/@fontsource-variable/inter/files/inter-latin-wght-normal.woff2 src/inter.ts "Inter Variable"
import inter from "./inter.ts";
const p = prepare(name, tableFace(inter, 16)); // a server, a worker, or before the font loads
globalThis.OffscreenCanvas = tableCanvas([inter]); // pretext, and so pretrunc/lines, without a browser
```

`scripts/metrics.ts` reads a font with fontkit, which opens WOFF2 and applies the font's GPOS kerning, and writes a module: each character's advance, every kerned pair among them, and the units per em. Inter's latin file gives 229 characters and 5,481 pairs: 63 KB, 18 KB gzipped, in 2.5 s. A variable font is read at its default instance, since fontkit's instancing loses the character map of a variable WOFF2.

A cut made from the table has to fit the text the browser lays out, so the table is never narrower than an engine. Contextual rules reach past a pair (Inter spaces a colon out between digits, 1.3 px at 15 px), so each character is laid out between each two of a set of neighbours, and whatever the three take beyond their pairs goes on its advance; kerning is measured against each glyph alone, so it never takes the widening back. A character the table doesn't cover counts as 1.5 em. Firefox rounds each glyph's advance, kerning to the next glyph included, to the nearest 1/60 px, its layout unit, so summed exactly the table ran narrow there by about 0.001 px a character, 0.4 px over 352 characters of Inter at 15 px, past the 1/64 px a cut keeps spare (#5). So `measure` rounds each glyph up to 1/60 px, which costs a cut at most that much a glyph in Chrome and WebKit, about 0.2%. The core's pair model still adds up: each pair is its first glyph's rounded advance and kerning plus the second's rounded advance, so a text's pairs less the glyphs between them sum to the text measured whole, and `prepare` still trusts it. The engine tests check that the table measures Latin text no narrower than each engine's canvas and within 10% of it, and that cuts made from it fit the engine's layout.

`tableCanvas` reads the size and the first family it has a table for from the context's `font`, line height and all, and falls back to the first table.

## DOM helpers (`pretrunc/dom`)

Shared by every adapter, so the React adapter later is thin.

- **One ResizeObserver** for all elements, dispatching through a `WeakMap<Element, callback>`. Its first notification arrives after layout and before paint, so an observed element is cut before its first frame.
- **Font from computed style,** read once per element and assembled from `font-style`, `font-weight`, `font-size` and `font-family`. The `font` shorthand reads back empty in some engines, and `font-stretch` reads back as a percentage, which canvas rejects.
- **Font epoch.** On `document.fonts` `loading`, once `document.fonts.ready` settles, every cached width is dropped and subscribers prepare and cut again. That includes pretext's: it keeps widths by font string, so a clamp prepared again after the font loaded still laid its text out in the fallback's widths, and a 2-line clamp in Inter at 14 px painted 3 (#4). `pretrunc/lines` hands pretext's `clearCache` to `forget` when it loads, so the core never imports pretext, and since pretext can't drop one font, a `forget` of one font drops all of pretext's widths. WebKit fires no `loadingdone` for a face loaded from script, so that event can't be the trigger. Before a web font loads, cuts use the fallback's metrics, which is right for what's on screen at that moment.

## Solid adapter (`pretrunc/solid`)

```tsx
<Truncate text={name()} at="middle" /> // observes width and font
<Truncate text={title()} at="end" width={column()} font={BODY_FONT} /> // no observer, no style reads
const handle = createCut({ text: name(), at: "middle" }) // ref, prepared and cut accessors
<Clamp text={body()} lines={3} expanded={open()} after={<button>{open() ? "less" : "more"}</button>} />
<FontProvider font={BODY_FONT} letterSpacing={0}><For each={rows()}>{(row) => <Truncate text={row.name} />}</For></FontProvider> // one font for the list
```

- `render="kept"` (default) paints the kept text and ellipsis, with the full text in `title`.
- `render="full"` paints all the text: the cut range sits in a `font-size: 0` span and the ellipsis in an `aria-hidden`, unselectable span, so copy, find-in-page and screen readers get the full text. The cut measures the ellipsis as a run of its own, since no kerning crosses into its element; `createCut` does the same with `separateEllipsis`, for markup of your own. Browser tests check in Chromium, Firefox and WebKit that it lays out within its box and that selecting it copies every character.
- `<Clamp>` lives in `pretrunc/solid/lines`, so a single-line page never loads pretext. Its `after` element, such as a "more" button, shows whenever the text is cut or expanded; Clamp observes its width and keeps that room free on the last line. Expanded, it shows every line, and `after` wraps to a line of its own when it doesn't fit.
- `createBox` is the part both share: the width, font and letter spacing given, then a `FontProvider`'s, or an element's, observed.
- Reading an element's font costs one `getComputedStyle` per row on mount, which for 5,000 rows took 4.5 ms in Chromium, 4 in Firefox and 5 in WebKit. A box reads font and letter spacing from one call; two calls, as it first did, took 8, 8 and 10 ms. `<FontProvider>` gives a list's font and letter spacing once, so its rows read nothing. It is the caller's word that the rows render in that font, and cuts follow it as they follow a `font` prop; a wrong one cuts wrongly, so it is opt-in, never inferred.
- Hints about the text itself, such as Latin only or no emoji, were measured and left out. pretrunc finds the script with one regex scan, 0.3 ms or less for 5,000 texts, and the costly work, measuring each new word once so cuts can be arithmetic, is the same in every script. A wrong hint would overflow to save about 20 ns.

## Not in v1

Each has an issue: the React adapter (#2) and the Inter metrics table measuring narrower than Chromium on Linux, so its cuts can overflow there (#3, a bug); until it is understood, the metrics engine tests don't run in Chromium on Linux, CI's runner included. A middle clamp can still show part of a word less at a wider width, in about one case in 100,000; the fixes cost flicker or a break every caller would have to add, so it stays (#1, closed). RTL text cuts in logical order and renders with the element's `dir`; mixed bidi text can reorder around a middle ellipsis, and v1 only documents that.

Kept for later, with no issue: features a caller opts into by import, so a bundler drops the rest. Bundling the core with each one cut out (2026-10-17) gave its share of the 2,430 bytes: protected matches 165, middle cuts 146, word backoff 95, letter spacing 48, trimming 18, an element ellipsis 7; all of them at once, 409, leaving 2,021. Text above U+0300 is 92 more but isn't optional, since cutting emoji or combining marks wrongly breaks the never-overflow promise. A plugin registry would spend part of the 409 on its own plumbing and add a call per cut. The cheaper shape is exports that tree-shake, such as a separate `cutMiddle` and `protect: marks(/[^/]+$/g)` from an imported helper. Either way it saves nothing through `<Truncate>`, which takes every option as a prop. Worth deciding once real users' bundles show whether 400 bytes matters.

## Proof

- **Properties** with effect's `Arbitrary` through `@effect/vitest`. In Node, against a fake font with known kerning and shaping, and pretext behind a fake `OffscreenCanvas`: never overflows; tight (with `words` and `trim` off, one more grapheme on a start or end cut overflows, and each side of a middle cut fills its share, where widths add up); steady (walking 20 px wider in quarter-pixel steps, with every option, neither side ever keeps less); history-free (a text cut at a run of widths cuts as a fresh copy would at each); identity; no grapheme split; protected matches whole or gone; clamps never take more lines than asked, fill the last line, start a start clamp's tail as early as fits, and hold steady as the width grows (at the start and end each end moves one way; in the middle, where head and tail trade on a shared line, a wider box shows no less text but for part of one word in rare cases, #1). In Chromium, Firefox and WebKit, against each engine's own layout: single-line cuts never lay out wider than the width, letter spacing included, Latin text keeps all but at most one grapheme of the widest fit, Latin text holds steady over quarter-pixel steps (a script that joins can paint a longer cut narrower, so no cut can promise it there), a protected path's middle cut switches once as its box widens, trusted text re-cuts without `measureText`, and clamps never wrap to more lines than asked, in both white space modes, with letter spacing, a width-only ellipsis and room after.
- **Where:** `vp run test` runs every engine test in Chromium, Firefox and WebKit. CI runs on Linux in Chromium and Firefox only: WebKit's Linux port shapes with HarfBuzz over FreeType where Safari uses CoreText, and the WebKit layout pretrunc works around is the same in both, so the macOS runs are the WebKit that matters. CI skips pushes that touch only Markdown or the demo, which the pre-commit hook type-checks.
- **Adapters:** one browser test per behaviour a person sees: resizing, the title, copying a full render, re-cutting after a web font loads, and a clamp keeping room for its button and expanding.
- **Mutants:** each test was checked by breaking the code it guards and watching it go red.
- **Size:** a test bundles each entry with Vite and rolldown, minified, compresses it with brotli and fails over budget.
- **Benchmarks:** against `pretext-truncate`'s `findTruncationPoint` and the pretext demo's `clampLines` and `layoutMiddle`, on the same inputs: a cold cut including `prepare`, a warm re-cut at a new width, and one resize frame over 5,000 rows.

`vp run test` runs every test in Node, Chromium, Firefox and WebKit, the bench aside.

## Benchmark results

`vp run bench` writes `bench/results.<engine>.md`, one engine at a time: run side by side, they take each other's CPU and the numbers swing by half. On an Apple M1 Pro, headless, median of 7 runs, ms per batch, every input distinct (2026-10-17). Each cold run measures a set of inputs no run has seen, built before the clock starts: engines keep their own cache of text widths, below anything `forget` or `clearCache` reaches, and rerunning one set, as the bench first did, let later runs find their unique words already measured. That favoured the demo and made WebKit's cold end cuts look slow (sprint-poker#66); with fresh sets, and alternating which runs first, pretrunc is ahead there.

pretrunc is the only one that never overflows. Cold end cuts are level with the demo in Chromium and ahead in Firefox and WebKit, middle cuts are 2 to 3 times faster cold and 2 to 6 warm, and warm cuts are level or better everywhere. Cold end clamps take 1.2 to 1.8 times the demo's. That isn't the never-overflow check, which end clamps never run: the demo lays the last line out again from pretext's word widths and cuts at a word, while pretrunc builds a per-character table of the last line, measuring characters, pairs and each new word once, so it can cut at any character with the kerning beside the ellipsis, letter spacing, `protect` and room after. Every paragraph here carries a number of its own, so each cold clamp measures at least one new word. Warm, both are level. The word measurements repeat pretext's own, but pretext's public `widths` fold in space kerning, measuring with the following space and emoji corrections, so a trust check against them could pass text canvas wouldn't, and its raw widths are internal. Profiling it found a clamp measuring the ellipsis afresh on every call, end clamps included, and `render="full"` doing the same on every cut: 500 of 1,219 `measureText` calls in 500 cold clamps. Both now use the cached width, and browser tests check that warm clamps and resizes measure nothing.

## Build order

1. Package scaffold: `packages/pretrunc`, workspace entry, subpath exports, size test, browser test project with three engines.
2. Measurer: char-code fast path, advance and kerning tables, calibration, tiers.
3. Single-line cut: end, start, middle and its three splits, protected spans, words, trim. Properties.
4. `pretrunc/dom`: shared observer, computed font, font epoch.
5. `pretrunc/solid`: `createCut`, `<Truncate>` with both renderings.
6. sprint-poker: Inter Variable through `@fontsource-variable/inter`, seat names cut in the middle.
7. `pretrunc/lines`: end, start, middle, confirmation, `roomAfter`, and `pretrunc/solid/lines`.
8. Benchmarks against the prior art.
